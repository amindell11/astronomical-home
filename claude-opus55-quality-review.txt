## Finding 1: the minimap berth lags the minimap by one frame of camera motion (correctness)

**Where:** `src/Asteroids3D/Assets/Scripts/UI/Objectives/ObjectiveMarkers.cs:63-70`

**Cause:**
- The code takes the minimap's world corners (`minimapRect.GetWorldCorners`) and projects them through `canvas.worldCamera` with `RectTransformUtility.WorldToScreenPoint`.
- The root HUD canvas is Screen Space – Camera (`UIOverlay.prefab:556`), so `canvas.worldCamera` is the UI camera. That camera is a child of the observer (`PlayerRig.cs:124`), which moves in `Update`.
- In `LateUpdate` the canvas transform hasn't caught up yet. `ShipStatusIndicator.cs:68` already notes this, and the pixel/scaleFactor recipe exists to avoid it.
- So the corners are still where the canvas was last frame, but they're projected through this frame's camera. `mapBounds` ends up off by one frame of camera travel.

**Effect:**
- The minimap glyph sits on `mapBounds.center`, so in steady flight it drifts off the minimap toward the trailing side. It snaps back when the ship stops.
- At ortho size 18 and normal cruise speed that's several pixels against a 13.75-unit glyph.
- The screen berth's "push below the minimap" check (line 79) reads the same offset `mapBounds`.
- Still captures can't show this, and the PlayMode test uses a Screen Space – Overlay canvas, so it isn't covered there either.

**Narrow fix (same rung as the existing recipe):**
- Work out the minimap rect in the canvas's own local space, not through the camera.
- Map each corner through `((RectTransform)canvas.transform).InverseTransformPoint(corner)` and subtract `canvasRect.rect.min`. The canvas and its children lag together, so this local position is exact even while the camera moves.
- Do the minimap clamp in canvas units, with `inset` not multiplied by `scaleFactor`. Assign the result straight to `anchoredPosition`.
- Multiply by `canvas.scaleFactor` only where the bounds are compared against screen pixels for the screen berth (line 79).
